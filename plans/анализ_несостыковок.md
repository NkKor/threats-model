# Отчёт об анализе кода проекта Threat Modeler

## Обзор проекта
Проект "Генератор моделей угроз ФСТЭК" представляет собой веб-приложение на FastAPI для фильтрации угроз безопасности информации согласно методике ФСТЭК 2021. Проект использует демо-версию списка угроз и имеет архитектурные проблемы, которые могут помешать корректной доработке на полной версии данных.

## Критические несостыковки и ошибки

### 1. Отсутствие конфигурационного файла .env.example
**Проблема**: В README указано копирование `.env.example` в `.env`, но файл `.env.example` отсутствует в проекте.
**Последствие**: Пользователи не могут настроить окружение по инструкции.
**Рекомендация**: Создать файл `.env.example` с примером переменных окружения.

### 2. Отсутствие файла consequence_map.yaml
**Проблема**: В `app/core/rules_loader.py` функция `load_consequence_map()` пытается загрузить `consequence_map.yaml`, но файл отсутствует в `data/rules/`.
**Последствие**: Функция возвращает пустой словарь, что может нарушить логику корреляции последствий.
**Рекомендация**: Создать файл `consequence_map.yaml` с картой соответствий согласно Таблице 3 ФСТЭК или удалить вызов этой функции, если она не используется.

### 3. Некорректная логика проверки интерфейсов
**Проблема**: В `app/core/correlation.py` функция `check_interfaces()` всегда возвращает `True` после проверки нескольких условий, но не фильтрует угрозы на основе интерфейсов.
```python
def check_interfaces(interfaces: List[str], threat: Threat) -> bool:
    if not interfaces:
        return True
    # ... проверки для отдельных интерфейсов
    return True  # Всегда True!
```
**Последствие**: Фильтрация по интерфейсам не работает, что может привести к включению нерелевантных угроз.
**Рекомендация**: Переработать логику функции, чтобы она возвращала `False` для угроз, которые не соответствуют выбранным интерфейсам.

### 4. Отсутствие middleware для сессий
**Проблема**: В `app/main.py` установлен `app.secret_key`, но не добавлен `SessionMiddleware`. В `app/api/endpoints/wizard.py` код использует `request.session`, который будет `None`.
**Последствие**: Сессии не работают, данные wizard не сохраняются между шагами.
**Рекомендация**: Добавить `SessionMiddleware` (например, `starlette-sessions` или `fastapi_session`) и настроить хранение сессий.

### 5. Несоответствие полей SystemProfile и проверок исключений
**Проблема**: В `SystemProfile` (schemas.py) есть поля, которые не используются в `check_exclusion_flags()` (например, `uses_virtualization`, `uses_l3vpn`, `uses_vipnet` и др.).
**Последствие**: Некоторые технологии не учитываются при фильтрации угроз, хотя должны.
**Рекомендация**: Проверить методику ФСТЭК на предмет соответствия и либо добавить проверки для этих полей, либо удалить неиспользуемые поля из схемы.

### 6. Потенциальные проблемы с типами данных
**Проблема**: В `app/api/endpoints/wizard.py` при обработке формы используется `form_data.get("pd_security_level")`, который может быть пустой строкой, а затем преобразуется в `int()` без проверки.
```python
"pd_security_level": int(form_data.get("pd_security_level")) if form_data.get("pd_security_level") else None,
```
**Последствие**: Если поле пустое, преобразование вызовет `ValueError`.
**Рекомендация**: Добавить обработку исключений или использовать `try-except`.

### 7. Отсутствие тестов
**Проблема**: В проекте нет тестов (папка `tests/` отсутствует).
**Последствие**: Невозможно проверить корректность логики фильтрации и API.
**Рекомендация**: Создать базовые тесты для ключевых модулей (correlation, validator, endpoints).

### 8. Проблемы с зависимостями
**Проблема**: В `pyproject.toml` указаны зависимости, но отсутствуют версии для некоторых пакетов (например, `pandas`). Также нет зависимостей для сессий.
**Последствие**: При развёртывании могут возникнуть конфликты версий.
**Рекомендация**: Зафиксировать версии всех зависимостей и добавить недостающие (например, `starlette-sessions`).

### 9. Логическая ошибка в уровне нарушителей
**Проблема**: В `app/core/correlation.py` функция `level_gte` использует обратную логику: `profile_rank <= threat_rank`. Согласно комментарию "Н1 > Н2 > Н3 > Н4 (Н1 - самый высокий)", но реализация может быть неверной.
**Последствие**: Фильтрация по уровням нарушителей может работать некорректно.
**Рекомендация**: Проверить логику согласно методике ФСТЭК и исправить при необходимости.

### 10. Отсутствие обработки ошибок в API
**Проблема**: В endpoints wizard нет валидации входных данных с использованием `validator.py`. Ошибки валидации не возвращаются пользователю.
**Последствие**: Пользователь может отправить некорректные данные без обратной связи.
**Рекомендация**: Интегрировать `WizardValidator` в endpoints и возвращать ошибки валидации.

## Архитектурные проблемы

### 1. Смешение ответственности
**Проблема**: Модуль `correlation.py` содержит как функции фильтрации, так и класс `CorrelationEngine` с валидацией профиля.
**Рекомендация**: Разделить ответственность: выделить валидацию в отдельный сервис, оставить в correlation только логику фильтрации.

### 2. Жёсткая связь с SQLite
**Проблема**: В `app/db/engine.py` используется SQLite с асинхронным драйвером, но путь к БД жёстко закодирован в настройках.
**Рекомендация**: Использовать абстракцию для поддержки других СУБД (например, PostgreSQL) в будущем.

### 3. Отсутствие слоя репозитория
**Проблема**: Запросы к БД разбросаны по `queries.py` и `init.py`, но нет единого интерфейса для работы с данными.
**Рекомендация**: Ввести паттерн Repository для инкапсуляции логики доступа к данным.

## Рекомендации по доработке на полную версию данных

1. **Масштабируемость данных**: Текущая структура БД рассчитана на демо-данные. При загрузке полной базы угроз ФСТЭК (более 2000 записей) необходимо:
   - Добавить индексы на часто используемые поля
   - Оптимизировать запросы с `selectinload`
   - Реализовать пагинацию для endpoints

2. **Производительность фильтрации**: Функция `filter_threats` проходит по всем угрозам линейно. Для больших объёмов данных следует:
   - Использовать кэширование результатов
   - Применить векторные операции через pandas/numpy
   - Рассмотреть предварительную индексацию угроз по характеристикам

3. **Валидация по методике ФСТЭК**: Требуется тщательная сверка с документами:
   - Проверить соответствие кодов объектов (О1-О17), методов (СП1-СП9), последствий (П1-П17)
   - Убедиться в правильности таблиц корреляции (Таблицы 3, 4, 8)
   - Верифицировать флаги исключений (Таблица 10)

4. **Безопасность**:
   - Добавить валидацию входных данных на всех уровнях
   - Реализовать защиту от CSRF (особенно важно для wizard)
   - Настроить CORS более строго (сейчас разрешены все origins)

## Приоритеты исправлений

1. **Высокий приоритет**:
   - Добавление SessionMiddleware
   - Исправление логики `check_interfaces`
   - Создание `.env.example`

2. **Средний приоритет**:
   - Интеграция валидации в endpoints
   - Создание consequence_map.yaml
   - Исправление потенциальных ошибок типов

3. **Низкий приоритет**:
   - Рефакторинг архитектуры
   - Добавление тестов
   - Оптимизация производительности

## Заключение
Проект имеет проработанную концепцию и хорошую структуру, но содержит критические несостыковки, которые необходимо устранить перед переходом на полную версию данных. Особое внимание следует уделить работе сессий и корректности логики фильтрации согласно методике ФСТЭК.

Рекомендуется провести дополнительный аудит кода с привлечением эксперта по методике ФСТЭК для обеспечения полного соответствия стандартам.
