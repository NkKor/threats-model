# Отчёт о доработке проекта

Дата: 2026-06-05. Основание: аудит проекта, сверка с источниками рабочего каталога
([`02_сравнение_источников.md`](02_сравнение_источников.md)) и требование сохранить суть
проекта — контейнер с веб-сервисом, который по опросу пользователя формирует итоговый
отчёт с предварительным просмотром прямо на веб-странице.

## 1. Кратко

Проект переведён из состояния «прототип с неработающим сквозным сценарием и выдуманными
справочниками» в состояние **работающего сервиса на реальных данных ФСТЭК**: 227 УБИ,
506 связей «УБИ × объект», 38 объектов, 9 способов реализации, 67 негативных
последствий, 14 типов ИС, 13 видов нарушителей, 10 тактик и 144 техники.

Проверено: **40 автотестов пройдено**, сквозной сценарий по HTTP (опрос → предпросмотр →
выгрузка XLSX/DOCX) отрабатывает на развёрнутом сервере.

## 8. Корректировка логики (раунд 3, по замечаниям заказчика)

### 8.1. Никакого хранения данных компании

* из схемы и кода удалён слой сохранённых моделей (`saved_models`, `/api/models/*`,
  страница «Модели», тесты) — это было единственное место, где профиль попадал в БД;
* в базе остаются только справочники и корпус УБИ (14 таблиц, 1251 запись) — проверено
  после полного прогона опроса: новых строк не появляется;
* cookie-сессия стала **сессионной** (`SESSION_MAX_AGE=0`, `max_age=None`): данные
  исчезают при закрытии браузера;
* кнопка **«Очистить данные»** добавлена на шаг 1 и шаг 5: очищает сессию, удаляет
  cookie и возвращает чистую первую страницу (`POST /api/wizard/clear`);
* на шаге 1 выведено явное уведомление, что данные опроса хранятся только в браузере.

### 8.2. Отчёт не сохраняется без команды

Экспорт выполняется только по нажатию кнопок «Экспорт в таблицу» (XLSX) или
«Экспорт в документ» (DOCX) либо ручным копированием со страницы предпросмотра.
Сервис не пишет отчёт ни в БД, ни в файловую систему; каталог `reports/` используется
только скриптом проверки `scripts/smoke_http.py`.

### 8.3. Убрана избыточная функциональность

Удалены или сокращены: сохранение/список/загрузка/удаление моделей, JSON-предпросмотр
(`/api/wizard/preview`, `/api/reports/preview`), `/api/wizard/profile`,
`/api/wizard/reset`, 10 отдельных эндпоинтов справочников (осталось три:
все справочники, типы ИС, нарушители с уровнями), дублирующие проверки в тестах.

### 8.4. Правила отчёта — в редактируемом файле

* создан `data/report-rules.txt` — обычный текст, правится в блокноте, изменения
  применяются без перезапуска;
* файл задаёт: общий заголовок, показ профиля системы, включение каждой таблицы,
  её заголовок и набор колонок (`column = поле | Заголовок | ширина | выравнивание`);
* один и тот же результат разбора используется страницей предпросмотра и выгрузками
  XLSX/DOCX — предпросмотр всегда совпадает с экспортом;
* ошибки в файле (неизвестное поле, битая строка, отсутствие файла) не ломают сервис:
  на странице отчёта выводится сообщение с номером строки, экспорт возвращает 500 с
  пояснением; такие случаи покрыты тестами;
* добавлен модуль `app/core/report_rules.py` и 12 тестов на разбор и применение правил.

### 8.5. Новый источник: «Уровни возможностей нарушителей по УБИ.xlsx»

* разобран и подключён к импорту: для каждого из 13 видов нарушителей определён
  уровень возможностей (Н1 — 5 видов, Н2 — 5, Н3 — 2, Н4 — 1);
* для каждого уровня сохранены потенциал и расширенный перечень способов реализации
  (СП.1–СП.26), а также состав нарушителей уровня;
* на шаге 2 уровень нарушителя показывается прямо в карточке вида, добавлена кнопка
  «Подставить уровень по выбранным нарушителям» и справка по уровням;
* **обнаружено расхождение источников:** расширенная нумерация СП.N из этого файла не
  совпадает с методической СП1–СП9 (например, методический СП2 «внедрение вредоносного
  ПО» = расширенный СП.4; расширенный СП.2 «недостатки конфигурации» в методике
  отдельной позиции не имеет). Чтобы не смешивать несовместимые перечни, расширенный
  список сохранён отдельным полем `methods_extended` и в отборе УБИ не участвует.
  **Требуется решение методиста о сопоставлении** — это единственный вопрос, который
  блокирует использование данного перечня в фильтрации;
* у уровня Н3 в источнике пустой столбец «Потенциал» — значение «Средний» выведено из
  наименования уровня и помечено флагом `potential_inferred`.

### 8.6. Автоматическое обновление схемы БД

Чтобы новые поля (`level`, `potential`, `methods_extended`, `source`) появлялись в уже
существующей базе, при старте выполняется сверка схемы: недостающие колонки добавляются
(`ALTER TABLE ADD COLUMN`), устаревшие таблицы удаляются, после чего справочные данные
перезаливаются. Данных пользователя в БД нет, поэтому перезаливка безопасна.
