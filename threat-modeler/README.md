# Генератор моделей угроз безопасности информации (ФСТЭК, 2021)

Локальный веб-сервис: пошаговый опрос пользователя → предпросмотр модели угроз
прямо на веб-странице → выгрузка итогового отчёта в XLSX/DOCX по явной команде.

Принципы работы с данными:

* **данные компании нигде не хранятся**: ответы опроса живут только в подписанной
  cookie-сессии браузера. Кнопка «Очистить данные» на первой странице (а также очистка
  кэша или закрытие браузера) полностью удаляет введённые данные и возвращает чистую
  первую страницу;
* **в базу данных ничего не пишется, кроме справочников и корпуса УБИ**: ни профиль
  системы, ни результат отчёта в БД не попадают;
* **отчёт сохраняется только по команде пользователя**: кнопка «Экспорт в таблицу»
  (XLSX), «Экспорт в документ» (DOCX) либо ручное копирование данных со страницы
  предпросмотра;
* сервис работает автономно (без внешних CDN и обращений в интернет)
  в обычном Python-окружении — Docker не требуется.

## Быстрый старт

### Windows / PowerShell (основной способ)

```powershell
cd threat-modeler
.\start.ps1            # окружение, зависимости, БД и сервер на 0.0.0.0:8080
```

Сервис: <http://localhost:8080> (Swagger: `/docs`, health: `/health`).
Скрипт выводит адреса, по которым сервис доступен коллегам из локальной сети
(`http://<IP-машины>:8080`); при необходимости разрешите входящие подключения
к порту 8080 в брандмауэре (команда `netsh` печатается при старте).

Параметры: `-Port 8080` (другой порт), `-RebuildVenv` (пересоздать окружение).

### Ручной запуск (любая ОС)

```bash
cd threat-modeler
python -m venv .venv
.venv\Scripts\activate            # Windows;  Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt

python -m scripts.import_sources  # собрать справочники и корпус из источников
python -m app.db.init             # создать БД и загрузить данные
uvicorn app.main:app --reload --host 0.0.0.0 --port 8080
```

Все команды выполняются из каталога `threat-modeler` — путь к БД (`DB_PATH`)
по умолчанию относительный (`./data/threats.db`).

## Как формируются данные

Единственный источник истины — источники рабочего каталога. Приложение не содержит
ручных списков объектов/последствий/методик — они собираются скриптом
`scripts/import_sources.py`:

| Источник | Что берётся |
|---|---|
| `справочники/бдму.xlsx` | **эталон корреляции**: 227 УБИ, 506 пар «УБИ × объект», для каждой пары — способы реализации, негативные последствия, тактики, техники |
| `справочники/ИС и негативные последствия.xlsx` | виды риска У1–У3, 67 последствий уX.Y и их применимость по типам ИС |
| `справочники/объекты.txt` | 38 объектов воздействия |
| `справочники/способы реализации.txt` | 9 способов реализации СП1–СП9 |
| `справочники/виды воздействия.txt` | 7 видов воздействия В1–В7 |
| `справочники/нарушители.txt`, `data/lib/Виды нарушителей.docx` | 13 видов нарушителей с категориями внешний/внутренний |
| `справочники/информационные системы.txt` | 14 типов информационных систем |
| `справочники/тактики_техники.csv` (фактически XLSX) | тактики Т1–Т10 и 144 техники |
| `сводная таблица.docx` | уровни возможностей нарушителей Н1–Н4 по каждой УБИ |
| `УБИ-объект.docx` | наименования УБИ и источник угрозы |
| `Уровни возможностей нарушителей по УБИ.xlsx` | уровень возможностей (Н1–Н4) для каждого вида нарушителя, потенциал уровня и расширенный перечень способов реализации уровня (СП.1–СП.26) |
| `data/lib/Негативные последствия.docx` | таблица 3 Методики: П1–П17 → объекты и виды воздействия В1–В7 |
| `data/lib/Способы реализации угроз безопасности информации.docx` | связь «тип интерфейса → способы реализации» |
| `data/lib/Уровни возможностей нарушителей.docx`, `Виды рисков.docx` | описания уровней Н1–Н4 и видов риска У1–У3 |
| `data/report-rules.txt` | правила формирования итоговых таблиц отчёта (правится вручную, не генерируется) |

Результат:

* `data/reference/*.yaml` — канонические справочники (генерируются, не редактируются вручную);
* `data/seed/threats_full.json` — корпус УБИ с корреляцией.

Проверка источников без записи: `python -m scripts.import_sources --check`.

### Дефекты источников, учтённые при импорте

* `справочники/тактики_техники.csv` — это XLSX с расширением `.csv` (сигнатура `PK`).
* `негативные последствия.txt`: код `п2.6` «слипся» с текстом `п2.5`, поэтому в файле
  `ИС и негативные последствия.xlsx` позиция объединена и остаток перенумерован
  (`у2.6` файла = `п2.7` исходного перечня). Импортёр восстанавливает 26 позиций для У2
  и сопоставляет их с применимостью по типам ИС; расхождение зафиксировано в
  `data/reference/consequences.yaml` в полях `source_code` / `source_note`.
* Таблица 3 Методики оперирует укрупнёнными последствиями П1–П17, а корпус — расширенным
  перечнем у2.1–у2.26. Соответствие строится монотонным выравниванием названий
  (динамическое программирование), результат и оценка схожести каждой пары сохранены в
  `data/reference/consequence_impacts.yaml` (поле `match`, минимальное значение 0.64);
  для 50 последствий риск-групп У1/У3 соответствия в таблице 3 нет — они не ограничивают
  отбор, это отражено в правиле R5.
* `объекты.txt` содержит 38 позиций — именно они используются (перечень О1–О17 из
  методики является уровнем обобщения и в корпусе не применяется).

## Шаги опроса

1. **О системе** — типы ИС (влияют на перечень последствий) и технологические признаки
   (подсказывают объекты на шаге 4), ПДн и уровень защищённости, доступ в Интернет.
2. **Нарушители** — 13 видов (внешние/внутренние) с указанием уровня возможностей
   каждого вида и кнопкой подстановки уровня по выбранным нарушителям; уровень
   задаётся отдельно для внешних и внутренних.
3. **Интерфейсы** — 10 типов; доступные через них способы реализации ограничивают отбор.
4. **Объекты и виды воздействия** — 38 объектов (с отметкой по технологиям шага 1) и
   необязательный фильтр по видам воздействия В1–В7.
5. **Отчёт** — предпросмотр: таблица 1 (виды риска и последствия) и таблица 2
   (перечень УБИ), поиск по перечню, экспорт, печать, кнопка «Очистить данные».

## Правила формирования отчёта: `data/report-rules.txt`

Состав итоговых таблиц задаётся обычным текстовым файлом, который правится в блокноте
(перезапуск сервиса не требуется):

```
[table2]
title = Таблица 2 – Перечень возможных (вероятных) УБИ для Системы
column = ubi_id | Идентификатор УБИ | 16 | center
column = ubi_name | Наименование УБИ | 60 | left
```

* `[report]` — общий заголовок документа и показ профиля системы;
* `[table1]`, `[table2]` — включение таблицы, её заголовок и колонки;
* колонка: `column = поле | Заголовок | ширина | выравнивание`;
* чтобы убрать колонку — удалите или закомментируйте строку, чтобы изменить порядок —
  поменяйте строки местами;
* список доступных полей приведён в шапке самого файла;
* при ошибке (неизвестное поле, битая строка) сервис не падает: на странице отчёта
  выводится сообщение с номером строки, а экспорт возвращает понятную ошибку.

Правила применяются и к странице предпросмотра, и к выгрузкам XLSX/DOCX, поэтому
предпросмотр всегда совпадает с экспортом.

## Правила корреляции

Пустой выбор по измерению = измерение не ограничивает перечень.

* **R1. Объекты.** УБИ проходит, если хотя бы одна её пара ссылается на выбранный объект.
* **R2. Последствия.** УБИ проходит, если хотя бы одно её последствие применимо к
  выбранным типам ИС (по таблице «ИС и негативные последствия»).
* **R3. Нарушители.** Для каждой заявленной категории с уровнем L: УБИ проходит, если
  указанный для неё уровень Li удовлетворяет `rank(Li) <= rank(L)` — нарушитель с более
  высокими возможностями реализует всё, что доступно более слабому. УБИ остаётся в
  перечне, если реализуема хотя бы одной заявленной категорией. Прочерк «―» в источнике
  означает «не ограничено».
* **R4. Интерфейсы.** УБИ проходит, если хотя бы один способ реализации её пар доступен
  через выбранные типы интерфейсов.
* **R5. Виды воздействия.** УБИ проходит, если хотя бы один выведенный для неё вид
  воздействия выбран; если виды воздействия определить не удалось — ограничение к ней
  не применяется.

Трактовка спорных правил настраивается без правки кода (см. `.env.example`):

| Настройка | Значения | Смысл |
|---|---|---|
| `LEVEL_SEMANTICS` | `capability` (по умолчанию), `strict` | «уровень нарушителя покрывает более слабые уровни» либо «уровень должен быть явно указан у УБИ» |
| `IMPACTS_SEMANTICS` | `keep` (по умолчанию), `exclude` | что делать с УБИ, для которых виды воздействия не определены таблицей 3 |

Текущие значения видны в `GET /api/version`.

## Хранение данных

| Что | Где хранится |
|---|---|
| Ответы опроса (профиль системы) | только в подписанной cookie-сессии браузера |
| Результат отчёта | нигде; формируется на лету при открытии шага 5 и при экспорте |
| Справочники и корпус УБИ | `data/reference/*.yaml`, `data/seed/threats_full.json`, БД `data/threats.db` |
| Правила отчёта | `data/report-rules.txt` (правится в блокноте) |

Кнопка «Очистить данные» (шаг 1 и шаг 5) очищает сессию, удаляет cookie и возвращает
чистую первую страницу. Закрытие браузера действует так же, поскольку cookie —
сессионная (`SESSION_MAX_AGE=0`).

## Настройки (.env)

Полный список — в `.env.example`. Ключевое:

* `SESSION_SECRET` — ключ подписи cookie-сессии; **обязательно** задать в production
  (`python -c "import secrets; print(secrets.token_urlsafe(48))"`);
* `SESSION_MAX_AGE=0` — сессионная cookie: данные опроса исчезают при закрытии браузера;
* `ENV=production` включает флаг `Secure` у cookie — сервис должен быть доступен по HTTPS
  (за обратным прокси); по HTTP сессия работать не будет;
* `CORS_ORIGINS` — по умолчанию пусто (только same-origin);
* `DATA_DIR` — каталог справочников, seed и файла `report-rules.txt`;
* `SEED_ON_STARTUP` — загрузка данных при пустой БД;
* `LEVEL_SEMANTICS`, `IMPACTS_SEMANTICS` — трактовка правил R3 и R5;
* `DB_ECHO` — вывод SQL-запросов.

## Ограничения и открытые вопросы

* Матрица «тип интерфейса → способы реализации» выведена из примера в методическом
  документе (не готовая таблица); источник указан в `data/reference/interfaces.yaml`
  (поле `source`), требует подтверждения методистом;
* трактовка прочерка «―» в уровнях нарушителей (сейчас — «не ограничивает») требует
  подтверждения; режим переключается настройкой `LEVEL_SEMANTICS`;
* **два перечня способов реализации**: методический СП1–СП9 (используется в корреляции
  УБИ из `бдму.xlsx`) и расширенный СП.1–СП.26 из файла «Уровни возможностей нарушителей
  по УБИ.xlsx». Нумерации не совпадают, поэтому расширенный перечень хранится отдельно
  (`methods_extended` у уровней Н1–Н4, `data/reference/violators.yaml`) и в отборе не
  участвует — требуется решение методиста о сопоставлении;
* у уровня Н3 в источнике не заполнен столбец «Потенциал» — значение «Средний»
  выведено из наименования уровня (в файле помечено `potential_inferred`);
* виды воздействия выводятся через таблицу 3 Методики: соответствие построено для
  17 укрупнённых последствий (охватывают 226 из 227 УБИ), для остальных 50 последствий
  риск-групп У1/У3 соответствия в источнике нет;
* негативные последствия вида `у1.*`/`у3.*`, не встречающиеся в `бдму.xlsx`,
  отображаются только в таблице 1 (виды риска и последствия).
